# dev-system 1.0 - release notes (draft)

dev-system 1.0 turns the shared dev environment into a small, self-running issue factory. You label an
issue `ready`, and the system designs it, builds it, reviews it, merges it and records what happened.
You step in only for decisions that belong to you.

These notes summarise the 0.11 to 0.18 releases, built and proven on 2026-10-08/09 (epic #223 and the
fixes its rollout turned up).

## How work flows now

1. **Claim.** The orchestrator claims a `ready` issue with a lease recorded on the issue itself. Two
   orchestrators can share one queue without double-claiming. A claim whose device goes quiet returns
   to `ready` once its lease expires.
2. **Design.** A designer agent explores the code and posts one design brief on the issue in a fixed
   shape: acceptance criteria, files, risk, test plan, sequencing, rollout and open decisions. The
   orchestrator keeps only a link to it.
3. **Build.** An implementer agent works in an isolated worktree from the brief and hands off to the
   no-mistakes pipeline (review, test, document, lint, PR, CI).
4. **Judge.** When a pipeline gate stops for a decision, an adjudicator agent gives a verdict on each
   finding (correct, wrong, nit, environment issue or duplicate) and proposes one action. The
   orchestrator acts on it, and the owner hears only about the decisions that are theirs.
5. **Merge.** A merge-guard script checks, in one step, everything that must be true before a merge:
   - the tested commit is the PR's commit
   - the PR links its issue correctly
   - GitHub CI is green
   - no gate is still waiting
   - the PR targets the right branch
   - GitHub will actually accept the merge

   A separate merge command then squash-merges exactly the verified commit.
6. **Roll out.** Each design brief says whether merging finishes the issue or whether it also needs a
   release and a "Run it" check on a real workspace. Issues that need a Run it stay open until the
   result is recorded on them.

## What is new

- **A dispatcher, not a do-everything session.** Judgement lives in focused agents (designer,
  implementer, adjudicator, fixer), each on the model that suits it. Rules that must never be
  forgotten live in scripts rather than in instructions, so a restart or a long session no longer
  loses them.
- **A durable record.** Every step from claim to merge is logged as an event and shipped to a central
  database. Ready-made queries answer:
  - how long each stage takes
  - how often work passes first time
  - how often the automated reviewer is wrong
  - how much each device merges
- **Safer merges by construction.** Merging and PR-body repair can only run from the main checkout, so
  delegated agents can check but never merge. The issue link, closing or referencing, comes from the
  design brief instead of being chosen by hand.
- **Releases that consumers pull.** Workspaces run a pinned, tagged release of the shared skills,
  never work in progress on main. Each release moves the pin and publishes fresh images. A workspace
  restart picks them up.
- **Watchers that notice problems.** Event-driven watchers wake the orchestrator for new work and for
  every pipeline change. That includes pipelines that are behind main, in conflict, or whose CI never
  started (for example, a repo with no CI workflow). A usage gate slows or pauses new work before the
  plan's usage runs out.
- **Onboarding sets up CI.** New repos get a CI workflow that runs exactly their lint and test
  commands, so their pipelines can reach merge-ready.

## Proven in practice

Every step above was released and run on a real workspace before the next one started. Those Run its
found and fixed five real defects before they reached other repos:

- events not reaching the database (#241)
- the merge guard missing its pipeline run (#243)
- the merge guard passing PRs that GitHub would refuse (#246)
- release PRs counting as issue completions in the sweeper (fixed in #220)
- issues closing before their Run it (#239)

## Known limitations

- A PR that goes green after another merge must be rebased and re-checked by hand. Whether to use a
  merge queue instead is an open decision (#189).
- The final step of the dispatcher epic is still to come: an audit of what remains in the
  orchestrator, a week-long two-orchestrator trial, and a go/no-go on the next architecture (#222).
- The orchestrator workspace runs the base image, so terraform checks run only in CI (#188).

## Upgrading

- Consumer repos: 1.0 is a future tag (the repo is at v0.18.0). Consumers pinned to
  `github:cbundy/dev-system#semver:0.x` must change the range to `semver:1.x` when 1.0 ships, then run
  `npm update @callum/dev-system && npx callum-dev update` and commit. This also moves the repo's
  plugin pin to the release. Until then, that command moves them to the latest 0.x.
- Workspaces: restart to pick up the latest image. Plugin updates install on start.
